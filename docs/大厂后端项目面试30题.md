# 阿尔茨海默病语音筛查项目：大厂后端面试 30 题

> 适用方向：Java 后端、分布式系统、AI 应用后端。  
> 回答原则：先说明当前实现，再说明生产演进；不要把设计方案说成已经上线的事实。

## 一、项目事实速览

这个项目是一个阿尔茨海默病语音风险筛查与健康科普系统，当前主要由以下部分组成：

- Spring Boot 3.5 / Java 17：用户、JWT/RBAC、音频元数据、筛查任务、报告、RAG 编排和静态前端。
- Python Flask Worker：WAV 质量检查、Whisper 中文转写、MFCC 与语言特征提取、DeepSeek 报告生成。
- MySQL + MyBatis：业务数据、任务状态、Outbox、消费去重、会话和消息，是业务最终真相源。
- RabbitMQ：异步筛查事件、重试与死信；链路按“至少一次投递 + 业务幂等”设计。
- Redis：登录失败计数、Token 会话和 RAG 会话上下文缓存；不是筛查结果的真相源。
- RAG：本地审核 FAQ 检索，可选 BGE-M3 Embedding + Qdrant；无可靠本地知识时可选 DeepSeek 联网搜索。
- 文件系统：当前保存音频、分析 artifact 和 PDF；这是多机部署前必须替换的关键单点。

当前已经实现的生产化雏形包括：异步任务 API、状态机、事务 Outbox、Publisher Confirm、持久化消息、消费者幂等、重试/DLQ、SHA-256 artifact 校验、有界线程池、多轮记忆和 SSE。尚未完成的生产能力包括：对象存储、正式容器镜像和 Kubernetes 清单、基础设施高可用、完善的限流/熔断、OpenTelemetry、生产密钥管理、自动迁移和临床模型验证。

面试回答推荐使用以下句式：

> “当前项目为了本地验证采用了 A，已经实现 B；如果按真实生产规模上线，主要瓶颈是 C，我会按 D、E、F 的顺序演进，并用 G 指标验证，而不是一开始就盲目拆很多微服务。”

## 1. 请用两分钟介绍这个项目，最有技术含量的部分是什么？

### 主回答

这是一个“语音筛查 + 医学科普 RAG”的 AI 应用后端。用户在明确知情同意后上传 PCM WAV，系统校验格式、时长和归属，创建持久化筛查任务。任务和 `screening.requested.v1` Outbox 事件在同一 MySQL 事务内写入；后台发布器将事件可靠投递到 RabbitMQ；Python Worker 做录音质检、Whisper 转写、MFCC/语言特征提取和谨慎的筛查报告生成；Java 消费分析结果，校验 artifact 的 URI 与 SHA-256，持久化报告，再异步生成 PDF。用户用任务 API 轮询状态，即使关闭页面，后台也能继续运行。

另一条链路是科普助手：先用本地确定性规则识别急症和问题类别，再检索审核知识；向量检索失败时降级到 classpath FAQ，LLM 失败时降级到知识原文。多轮对话以 MySQL 为真相源、Redis 为可丢缓存，每 10 轮生成滚动摘要，通过 SSE 输出可见正文，同时过滤模型思考内容。

我认为最有含金量的不是“调用了大模型”，而是围绕慢任务和不可靠下游做了状态机、Outbox、幂等消费、重试/DLQ、资源隔离、可降级和敏感数据边界。

### 追问展开

- 项目目前是生产化原型，并非临床诊断系统；当前 AI 引擎仍返回 `INCONCLUSIVE`，不把 LLM 输出伪装成患病概率。
- 当前同步筛查旧接口仍存在，生产会逐步下线，统一为 `202 Accepted + taskId` 的异步接口。
- 可以主动给出一条量化目标：API 受理 P95 小于 300 ms；筛查完成时间按阶段监控；任务成功率、队列年龄、DLQ 数、模型成本和质量覆盖率作为核心指标。数值需经压测确定，不能声称已经达到。

## 2. 一次异步语音筛查的完整调用链是什么？为什么要这样设计？

### 主回答

完整链路是：

1. 用户上传音频。服务端校验知情同意版本、RIFF/WAVE 头、PCM 编码、采样率、声道、位深、文件大小和时长，生成不可猜测的服务端文件名，并保存音频元数据。
2. 客户端携带 `Idempotency-Key` 创建筛查。后端校验音频归属、文件存在、未生成报告、用户活动任务数未超限。
3. 同一数据库事务写入 `screening_task(QUEUED)` 和 `outbox_event(NEW)`，随后立即返回 `202`、任务地址和 `Retry-After`。
4. 定时 Outbox Publisher 查询待发布事件，发送到 RabbitMQ，等待 Publisher Confirm，并检查 mandatory return；确认成功后才标记 `PUBLISHED`，失败则指数退避重试。
5. Python Worker 手动 ACK 消费，按阶段发布状态事件，完成后把大结果写为 `analysis.json`，只在消息里发送 taskId、artifact URI 和 SHA-256。
6. Java 结果消费者验证 event schema、任务/用户/音频一致性、artifact 路径、哈希和字段范围，在本地事务中保存报告、更新任务并写入 PDF Outbox。
7. PDF 消费者使用临时文件生成并原子移动，保存 PDF 元数据，任务最终进入 `COMPLETED`。

这样设计的核心是把长耗时 GPU/外部 API 工作从 Tomcat 请求线程剥离，允许削峰、重试、独立扩缩容和退出页面继续执行；同时让 MySQL 保存可恢复状态，MQ 只负责传输。

### 追问展开

- 消息中不放原始音频和完整报告，避免 RabbitMQ 成为大文件与敏感数据仓库。
- 状态查询读取 MySQL，不依赖消息是否还在队列中。
- 每个阶段都有明确输入、输出和版本，未来可以把当前组合 Worker 拆为质检、ASR、特征、LLM、PDF 多个 Worker 池。

## 3. 如果把项目上线成真正的分布式系统，你会如何拆模块和分配服务器？

### 主回答

我不会一开始拆十几个微服务。当前业务量和团队边界下，先做“无状态模块化 API + 独立 AI Worker + 外置状态”更合理：

```text
用户
  -> CDN/WAF/HTTPS Ingress
  -> Spring Boot API x 2+
       -> MySQL 高可用：业务真相、任务、Outbox
       -> Redis 高可用：Token、限流、可重建缓存
       -> 对象存储：音频、artifact、PDF
       -> RabbitMQ 三节点 Quorum Queue
            -> 质检/轻特征 CPU Worker 池
            -> Whisper GPU Worker 池
            -> LLM I/O Worker 池
            -> PDF CPU Worker 池

RAG：Embedding GPU/CPU 服务 -> Qdrant 多副本
      知识索引构建 Job -> 版本化 collection/alias
所有组件 -> OpenTelemetry Collector -> Metrics/Logs/Trace
```

Spring Boot API 至少两个跨故障域副本，不保存本机业务文件；用户、权限、任务受理、报告权限和 RAG 编排先保留在一个模块化单体中。Python Worker 按资源特征分池，GPU Worker 不和普通 API 抢 CPU/内存。MySQL、Redis、RabbitMQ 和对象存储优先使用多可用区托管服务；Qdrant 设置 shard、replication factor 和节点反亲和。

API 可按 CPU、请求数和延迟扩容；Worker 更适合按队列深度、最老消息年龄和阶段耗时扩容。比如 Whisper 单任务若平均占用一张 GPU 20 秒，一张卡安全并发为 1，则单卡约 0.05 task/s；高峰到达率 0.2 task/s 时至少需要 4 张卡，再加故障和波动余量。实际数值必须用压测测出。

### 模块协调

- MySQL 中的任务状态是最终真相，RabbitMQ 负责解耦与削峰。
- 服务间使用版本化事件 schema；大对象只传 object key 和 checksum。
- 采用至少一次投递，各消费者用 `(consumerName,eventId)` 和业务唯一键幂等。
- 通过 traceId/taskId 贯穿 HTTP、Outbox、MQ、Worker 和报告。
- 对象存储删除、报告删除等跨资源操作用删除任务/事件和补偿，不声称能靠本地事务实现原子性。

### 为什么不是立刻全微服务

拆分依据应该是团队所有权、发布频率、故障隔离和资源曲线，而不是类的数量。AI Worker 已有明显的 GPU/CPU/I/O 边界，适合独立部署；用户、报告和任务当前强事务关联较多，过早拆分会引入分布式事务和接口治理成本。

## 4. 为什么不用 `@Async` 或线程池直接后台跑，而要引入 RabbitMQ？

### 主回答

`@Async` 只把任务放进单个 JVM 的内存队列，进程重启任务就可能丢失；它缺少持久任务状态、跨实例竞争、可靠重试、DLQ、削峰和独立扩缩容。这个项目的 Whisper 和 LLM 可能耗时数十秒，并涉及 GPU 与外部 API，不能让任务生命周期绑定某个 API 实例。

RabbitMQ 提供持久化队列、消费者确认、prefetch、路由、重试和死信，使 API 快速受理后退出。MySQL 又保存任务状态和 Outbox，即使 MQ 暂时不可用，也能恢复发布。线程池仍然需要，但它用于限制单个消费者进程内部并发，不承担持久化任务队列职责。

### 什么时候线程池反而够用

- 任务很短、丢失可接受、无需跨实例、无需用户查询进度。
- 例如 RAG 每 10 轮后的摘要刷新，目前用独立有界线程池，因为摘要失败可以在后续轮次补做，MySQL 原消息还在。
- 即便如此也必须设置有界队列、拒绝策略和优雅停机，避免默认无界队列导致内存膨胀。

## 5. 事务 Outbox 解决了什么问题？它能保证 exactly-once 吗？

### 主回答

如果业务先提交 `screening_task` 再发 MQ，进程可能在两步之间宕机，数据库有任务但消息丢了；如果先发消息再提交数据库，消费者可能看到一个不存在或回滚的任务。这就是数据库与 MQ 双写不一致。

项目在同一个 MySQL 本地事务里写任务和 Outbox。只要事务提交，两条记录必然同时存在；后台发布器把 Outbox 投递到 MQ，收到 broker confirm 且消息可路由后标记已发布。发布失败就保留记录并重试，因此实现的是可靠的最终投递。

它不能保证端到端 exactly-once。典型窗口是 broker 已收消息，但发布器在标记 `PUBLISHED` 前宕机，恢复后会重复发送。因此正确语义是 at-least-once delivery，加消费者幂等得到 effectively-once 的业务结果。

### 当前实现与生产改进

- 当前已实现：事务写 Outbox、Publisher Confirm、mandatory return、失败指数退避。
- 当前薄弱点：多 API 实例的 Publisher 可能同时查询同一批 `NEW` 记录，造成重复发布；虽然消费者幂等可保证结果正确，但会浪费资源。
- 生产改进：用 `SELECT ... FOR UPDATE SKIP LOCKED` 在短事务中领取记录，或增加 `PROCESSING/lease_owner/lease_until` 租约；也可使用 Debezium CDC 读取 Outbox。无论哪种方式，消费者幂等仍不能删除。
- 还需归档/清理已发布 Outbox，监控最老未发布事件年龄，而不只看数量。

## 6. RabbitMQ 已经 ACK 了，为什么还需要消费者幂等？你如何实现？

### 主回答

ACK 只表示某次投递已经由消费者确认，不表示消息永远只投递一次。消费者处理完成但 ACK 在网络中丢失、连接断开、发布方重复发送、人工重放 DLQ，都会导致重复消息。

项目为每个逻辑事件生成确定性 `eventId`，Java 消费者在业务事务内先执行：

```sql
INSERT IGNORE INTO consumed_event(consumer_name,event_id,processed_at)
```

返回 0 表示该消费者已处理过，直接返回。`consumer_name` 被放进主键是因为同一事件可被状态投影、结果持久化等不同消费者各处理一次。报告表和 PDF 表还以 `screening_task_id` 建唯一键，形成第二层业务幂等；artifact 采用固定 taskId 路径和原子覆盖。

### 关键事务边界

“领取 consumed_event”和业务落库必须在同一个数据库事务中。若先提交去重记录，再处理业务，处理中途失败后重投会被误判为已完成；若业务提交后去重记录未提交，则可能重复产生业务结果。项目的 Java Listener 使用 `@Transactional` 覆盖二者，这是必要条件。

Python Worker 的 artifact 幂等是“已有同模型有效 artifact 就直接重新发布完成事件”。生产拆阶段后，每个阶段还应有独立的产物唯一键和幂等状态，避免昂贵的 Whisper/LLM 重复执行。

## 7. 消息乱序会怎样？如何保证任务状态不会从 70% 回退到 20%？

### 主回答

RabbitMQ 只能在特定队列和单消费者等条件下提供局部顺序；一旦多消费者、重试队列、不同路由并行，不能依赖全局顺序。项目的状态更新采用“单调状态投影”：

```sql
UPDATE screening_task
SET status=?, progress=?, version=version+1
WHERE id=?
  AND progress <= ?
  AND status NOT IN ('COMPLETED','FAILED','CANCELLED','CANCEL_REQUESTED');
```

所以旧的 20% 事件晚于 70% 到达也不能回退进度；终态也不会被普通阶段覆盖。重复事件则由 `consumed_event` 拦截。

### 进一步改进

- 只比较 progress 还不够表达所有状态关系，例如 `RETRY_WAIT` 与原阶段、失败后人工重试的新 attempt。生产应在代码中定义合法状态转移表，并把 `attempt` 或 `state_version` 纳入条件。
- 可使用 `WHERE version=?` 的乐观锁或 `WHERE attempt=? AND stage_seq<=?`，检查更新行数；不合法事件记录审计而不是静默覆盖。
- 对同一 taskId 需要严格有序时，可以按 taskId 一致性哈希到固定分区；但 RabbitMQ topic queue 本身不是 Kafka partition，通常仍以幂等状态机抵抗乱序更稳健。

## 8. 如何设计重试、延迟队列和死信，避免“重试风暴”？

### 主回答

先做错误分类，而不是所有异常无脑重试：

- 永久错误：非法 schema、越权、文件不存在、格式错误、路径越界、模型配置错误，直接发布失败事件并进入 DLQ，不重试。
- 短暂错误：网络抖动、下游 429/5xx、临时对象存储错误，可有限重试。
- 不确定错误：先记录可观测上下文，再按白名单决定是否重试，避免持续消耗第三方费用。

当前 Python Worker 最多重试 3 次，把消息发到带 TTL 的 retry queue，10 秒后通过 dead-letter exchange 回到工作队列；Java Listener 使用 1s、3 倍、最多 10s 的有限本地重试，耗尽后拒绝且不 requeue，由 DLX 收集。Outbox 发布失败使用上限 300 秒的指数退避。

生产上我会增加指数退避加随机抖动，例如 `min(cap, base*2^attempt) + jitter`，为 429 尊重 `Retry-After`；按下游设置独立队列和并发上限；设置最大尝试次数、最大消息年龄和预算。DLQ 不能只是“垃圾桶”，要告警、展示失败原因、支持经过权限审核的幂等重放，并防止毒消息无限回环。

## 9. 高峰期上传大量音频，如何做背压、限流和容量规划？

### 主回答

我要同时在入口、队列和 Worker 三层做背压：

1. 入口：按用户/IP/租户做 Redis 令牌桶，限制上传 QPS、字节速率和任务创建频率；当前代码已有“每用户最多 2 个活动任务”，但生产需要原子限流。
2. 队列：消息只放引用，设置持久化、prefetch 和最大长度/磁盘水位告警；监控 ready、unacked、最老消息年龄。
3. Worker：按 CPU/GPU/外部 API 分池，设置有界并发。当前 Python `prefetch=1` 且单进程串行，安全但吞吐低；Java 结果、状态、PDF 使用不同固定线程池，避免 PDF 阻塞状态更新。

容量不能只看 QPS。设到达率为 λ、每个 Worker 平均处理率为 μ，根据稳定条件要求总服务率 `c*μ > λ`，再用排队时间和突发系数留余量。例如 Whisper 平均 20 秒/条、单卡并发 1，则 μ=0.05 条/秒；峰值 λ=0.2 时理论至少 4 卡，生产可能配 5～6 卡并根据队列年龄扩缩容。LLM 池还受 RPM/TPM 和成本预算约束。

### 当前代码的竞态

`countActiveByUser >= 2` 再插入任务是“先查后写”，两个并发请求可能都通过。生产可选：

- 为用户配额行执行 `SELECT ... FOR UPDATE`；
- Redis Lua 原子占用名额，任务结束释放，并有超时修复；
- 数据库维护 active counter，用条件更新 `active_count < limit`；
- 最简单时按 userId 获取短时分布式锁，但要处理过期和 fencing token。

## 10. 项目里的线程池如何设计？`CallerRunsPolicy` 有什么利弊？

### 主回答

项目把结果持久化、状态投影、PDF 和对话摘要分开：结果与状态默认并发 2，PDF 并发 1，队列容量 20；摘要并发 2、队列 100。固定大小和有界队列能避免突发流量创建无限线程或堆积无限任务。

RabbitMQ Listener 线程池使用 `CallerRunsPolicy`：线程池饱和时，由提交任务的调用线程执行，能自然减慢消息拉取，形成背压并尽量不丢任务；但代价是 RabbitMQ 容器线程可能被耗时业务占住，心跳和吞吐变差，所以还必须配合小 prefetch、合理 consumer 数、执行超时和队列监控。

对话摘要使用 `AbortPolicy`，因为摘要是可补偿的优化任务：饱和时快速拒绝，调用方捕获异常，后续轮次可重新摘要，不应反过来拖慢用户 SSE 主链路。

### 参数如何确定

- CPU 密集型：线程数接近可用核数，避免上下文切换。
- I/O 密集型：可按 `Ncpu * (1 + wait/compute)` 估算起点，再以压测、连接池和下游限额校准。
- 线程数不能超过数据库连接池、HTTP 连接池和外部 API 并发能力，否则只是把等待从队列转移到连接池。
- 每个池必须暴露 active、queue size、rejected、task duration，并设置优雅停机等待时间。

## 11. 当前 Python Worker 是串行组合流水线，如何利用多核和 GPU 扩展？

### 主回答

当前组合 Worker 一条消息依次完成质检、Whisper、特征和 LLM，`prefetch=1`。它作为首版有两个优点：状态和错误边界简单、不会因并发把 GPU 打爆；缺点是 CPU、GPU 和网络等待串在一起，吞吐由最慢阶段决定，某阶段故障会占住整个 Worker。

生产演进时我会按资源曲线拆部署单元，而不是简单把 Python 线程数调大：

- 质检与轻量语义特征：CPU Worker，多进程扩展。
- Whisper：GPU Worker，通常一进程绑定一个 GPU 或明确的显存份额，用队列长度扩容。
- MFCC/librosa：CPU Worker，可与质检合并或独立批处理。
- LLM：I/O Worker，受第三方 RPM/TPM、超时和预算控制。
- PDF：Java CPU Worker，和 API 进程分离。

各阶段输出不可变 artifact，并发布版本化完成事件。这样某阶段可独立重试和扩容，也避免重跑前面已经成功的昂贵阶段。

### Python 并发注意点

- Python 线程对纯 Python CPU 代码受 GIL 影响；NumPy、CTranslate2 等原生库可能释放 GIL，但仍应基准测试，CPU 密集任务通常用多进程。
- 多进程各加载一份大模型会占用大量显存，不能按 CPU 核数盲目开进程。
- 模型应在进程内复用；当前 Whisper 用 `lru_cache(maxsize=1)` 懒加载，但生产更适合启动时加载并通过 readiness 阻止未就绪实例接流量。
- GPU OOM 属于容量或输入问题，通常不应无上限重试；可降级到更小模型/CPU或明确失败。

## 12. 为什么本地文件系统阻碍横向扩容？你会如何迁移到对象存储？

### 主回答

当前 API 把音频写到 `data/audio`，Python 从同一路径读，分析写 `data/screening-artifacts`，Java 再读并生成 `data/pdf`。单机可行，但多节点时上传落在 API-A，本地 Worker-B 看不到文件；Pod 重建还可能丢数据。因此业务计算节点必须无状态化。

我会引入 `ObjectStorageService` 抽象，用 S3/MinIO/云对象存储：

1. API 创建上传会话，校验用户和配额，返回短期预签名 URL；客户端直传，减少 API 带宽和堆内存压力。
2. 上传完成后服务端通过对象 HEAD/回调确认大小、Content-Type、checksum 和 object key，再创建音频元数据。
3. MQ 只传 bucket/key/versionId/SHA-256，不传二进制。
4. Worker 使用工作负载身份读取对象，写入以 taskId 和阶段版本命名的不可变 artifact。
5. 下载前先校验数据库归属，再返回短期预签名 URL；对象桶不公开。

### 一致性与安全

- object key 由服务端生成，不能接受用户提供的任意路径；限制前缀、大小、格式、存储类型和过期时间。
- 使用服务端加密/KMS、版本控制、生命周期、审计日志和最小权限策略。
- 数据库提交与对象写入不能共用 ACID 事务：上传采用“临时对象 -> 校验 -> 元数据提交 -> 正式可见”，失败由定时清理孤儿对象；删除采用 tombstone/outbox 事件、幂等清理和对账任务。
- 不能仅信任 Content-Type；仍要解析 RIFF/WAVE 和音频结构，必要时做恶意文件扫描。

## 13. `screening_task` 表为什么这样设计？索引和唯一约束有什么作用？

### 主回答

`screening_task` 同时承担任务真相和用户查询视图，核心字段有 taskId、userId、audioRecordId、idempotencyKey、status、stage、progress、attempt、version、modelVersion、traceId 和各时间戳。

关键约束：

- 主键 `id`：定位任务。
- 唯一键 `(user_id,idempotency_key)`：同一用户重复请求只产生一个任务。
- 唯一键 `audio_record_id`：当前业务规定一段音频最多一个筛查任务。
- `(user_id,requested_at)`：支持用户任务列表按时间分页。
- `(status,updated_at)`：支持扫描卡住任务、统计和恢复。
- progress CHECK、外键与报告的 taskId 唯一键：防止非法状态和重复结果。

### 可能的追问

1. 为什么不只用 Redis 存任务？Redis 数据可过期或故障，无法承担报告审计与恢复；MySQL 是真相源，Redis只能缓存热点视图。
2. UUID v4 做聚簇主键有什么问题？随机 CHAR(36) 空间大、页分裂多。规模上来可改 UUIDv7/ULID 或 `BINARY(16)`，兼顾趋势递增与全局唯一。
3. `LIMIT/OFFSET` 深分页怎样优化？改为基于 `(requested_at,id)` 的游标分页，并建立相同顺序的联合索引。
4. 唯一 `audio_record_id` 是否妨碍模型重跑？是。若业务需要同一音频按新模型复评，应改为 `(audio_record_id, screening_version)` 或单独建 screening run，保留历史可追溯性。

## 14. Redis 在项目中承担什么角色？Redis 宕机系统应该怎样表现？

### 主回答

当前 Redis 保存三类数据：登录失败计数、Token 会话/单设备登录映射、RAG 会话上下文缓存。设计原则应该是“能从权威数据重建的放 Redis，任务结果和报告不只放 Redis”。RAG 已经遵循这一点：Redis 读写失败会回退 MySQL，缓存异常不影响历史消息真相。

但鉴权链路目前把 `TOKEN:{token}` 是否存在作为有效会话条件，所以 Redis 宕机会导致受保护 API 无法登录，属于安全优先的 fail-closed，但也使 Redis 成为可用性关键依赖。生产可采用托管高可用 Redis或主从 + Sentinel/Cluster，并明确两种方案：

- 保持可撤销会话：Redis 不可用时拒绝请求，保证登出和单设备登录语义；需要高可用与容量保障。
- 纯短期 JWT：网关本地验签，在 Redis 故障时仍可服务，但撤销能力变弱；可用短 access token + refresh token rotation、撤销版本号折中。

### 缓存问题

- 防穿透：参数校验、负缓存或布隆过滤器，具体取决于数据规模。
- 防击穿：热点 key 使用 single-flight/互斥重建。
- 防雪崩：TTL 加随机抖动、分批预热、限流和降级。
- 会话缓存 key 应含 owner/版本并加密或最小化内容；当前健康对话是敏感信息，不应在普通 Redis 裸存太久。

## 15. 用户取消一个正在执行的筛查任务，怎样避免结果仍被保存？

### 主回答

取消在分布式系统中通常是协作式、最终生效，而不是瞬间杀死远端计算。项目把任务先改为 `CANCEL_REQUESTED`；结果消费者和 PDF 消费者在落库前检查该状态，若已请求取消则转为 `CANCELLED` 并丢弃后续结果。因此即使 Worker 已经完成昂贵计算，也不会继续生成用户可见报告。

生产上我会在每个安全检查点检查取消：开始下载前、ASR 前、LLM 前、写 artifact 前。可通过数据库查询、Redis 短期取消标志或 `screening.cancelled.v1` 控制消息传播；但 Redis 只能加速，最终仍以 MySQL 状态为准。

### 竞态处理

- “完成落库”和“取消”并发时，应在一个条件更新或行锁事务里决定胜者，例如 `UPDATE ... WHERE status IN (...)` 并检查影响行数。
- 若结果已经进入 `COMPLETED`，当前 API 返回冲突，不再声称可取消；用户若要删除，应走数据删除流程。
- 对已经发出的外部 LLM 请求通常无法强制撤回，只能停止后续落库和展示，并记录费用；所以在昂贵阶段前检查取消最划算。
- 任务取消后要清理临时 artifact，清理由幂等异步任务负责，不能在 HTTP 请求中无限等待。

## 16. PDF 文件和数据库记录如何保持一致？本地事务够吗？

### 主回答

数据库事务无法回滚文件系统或对象存储操作，所以严格原子性不存在。当前异步 PDF 生成采用固定 taskId 文件名，先写 `.tmp`，关闭文件后使用 `ATOMIC_MOVE + REPLACE_EXISTING`，不支持原子移动时再降级；然后计算 SHA-256 和大小，保存带 taskId 唯一键的 PDF 元数据。这能避免用户读到半个 PDF，也使消息重投覆盖同一确定性目标。

仍然存在两个失败窗口：

- 文件成功但数据库失败：留下孤儿文件。
- 数据库成功后文件被外部删除或损坏：留下悬空记录。

解决方案是状态机 + 幂等 + 对账，而不是分布式锁：元数据可设 `GENERATING/AVAILABLE/DELETE_PENDING/FAILED`；生成后校验 hash 再标 AVAILABLE；定时任务扫描临时文件、孤儿对象和 hash 不一致，重建或告警。对象存储场景使用不可变 key/version，并让元数据指向确定版本。

当前同步 `/audio/pdf/save` 允许客户端提交 transcription/report 再生成 PDF，生产应下线或改为只根据服务端已保存报告生成，否则客户端可以篡改报告内容。

## 17. RAG 问答的完整流程是什么？为什么先路由再检索？

### 主回答

流程是：输入长度校验 -> 本地关键词路由 -> 急症/越界短路 -> 按类别检索 -> LLM 基于检索上下文生成 -> 过滤思考内容 -> 附免责声明和来源 -> 失败降级。

先路由有三个目的：

1. 安全：突发言语障碍、单侧无力、意识异常等急症必须本地立即返回 120 提示，不能依赖向量库和 LLM。
2. 精度：Qdrant 查询按 category payload 过滤，减少相似但主题不符的知识。
3. 成本与边界：超出阿尔茨海默病科普范围直接拒答，避免不必要的 Embedding/LLM 调用。

检索有两级：向量检索开启时用 BGE-M3 生成 query vector，在 Qdrant 以 Cosine 搜索并用 0.72 阈值过滤；服务或索引异常就回退 classpath FAQ 的关键词、包含关系和 bigram 评分。检索为空时才尝试受控联网；联网也不可用则明确回答“资料不足”，而不是让模型凭参数记忆编造。

### 局限与改进

当前路由是关键词规则，优点是可解释、急症可确定性控制，缺点是同义表达和否定语境召回不足。生产可保留高召回安全规则，再增加小模型分类器；离线评估急症 recall、类别 macro-F1、误拒率，并让低置信度进入安全兜底。

## 18. 向量检索为什么还要关键词检索和阈值？如何评估 RAG？

### 主回答

向量检索擅长语义同义，但可能把“语义相近、事实不相关”的段落排高；关键词/BM25 对药名、指标、缩写和精确实体更稳。生产更合理的是混合检索：BM25 和 dense 并行召回，各取 top-N，用 RRF 融合，再以 reranker 排序，最终选 top-K。任何一段失败都可以降级到剩余检索器。

阈值不是越高越好。太低会把无关知识喂给 LLM，增加错误回答；太高会降低覆盖率并频繁联网或拒答。当前 0.72 只是配置起点，必须用标注集校准，而不能凭感觉。

### 评估体系

- 检索：Recall@K、MRR、NDCG、无答案拒答准确率、分类内误命中率。
- 生成：事实支持率、引用正确率、答案完整性、幻觉率、安全违规率。
- 系统：P50/P95/P99、Embedding/Qdrant/LLM 分阶段耗时、降级率、费用。
- 数据集应包含同义改写、错别字、多轮指代、无答案、跨域、急症和 prompt injection。

先建立 300～1000 条经审核基线，再逐项灰度“混合召回 -> reranker -> 查询改写”，每次只改一个变量，才能归因质量变化。

## 19. 为什么不应该在用户第一次查询时初始化 Qdrant？如何做知识索引发布？

### 主回答

当前 Qdrant Retriever 可以在第一次请求时对 classpath FAQ 批量 Embedding、建 collection、upsert 和建 payload index，并用进程内锁避免本实例重复初始化。它适合本地演示，但生产有明显问题：首请求延迟很高；多 API 实例仍会并发初始化；Embedding 或建索引失败会把业务 readiness 和用户流量耦合；原地更新可能出现半新半旧索引。

生产应把知识库视为受治理的源数据，把 Qdrant 视为可重建派生索引：

```text
知识编辑 -> 医学审核 -> 发布版本 v42
-> 独立 Job 切块、Embedding、写 collection_v42
-> 数量/checksum/readiness 校验
-> 离线检索评测
-> 原子切换 alias active_knowledge -> collection_v42
-> 灰度监控，失败切回 v41
```

API 启动只检查 alias 指向的索引是否可用，不负责构建。Embedding 模型版本、切块策略、知识版本和向量维度一起进入索引版本；更新时双写或重建新版本，绝不在活动 collection 上做不可控的大规模覆盖。

### Qdrant 不可用时

在小知识库下回退审核 FAQ 检索；规模更大时可回退只读 BM25。告警应区分 Qdrant 连接失败、Embedding 失败、空索引和阈值拒绝，避免把正常“无相关知识”当系统故障。

## 20. 多轮对话记忆如何实现？如何解决并发提问和缓存一致性？

### 主回答

MySQL 保存 conversation、每轮 USER/ASSISTANT 消息和摘要块，是真相源；Redis 保存序列化的上下文缓存，失败就回源 MySQL。每个对话最多 100 轮，每 10 轮把新增完整对话压缩为一段摘要，再与滚动摘要合并；Prompt 中明确“记忆只用于指代，不是医学事实来源，冲突时以审核知识为准”。这控制了 token 成本，也降低旧对话对当前事实的污染。

并发控制不是 Java `synchronized`，因为多实例无效。数据库用单条条件更新获取生成权：仅当 `generation_status=IDLE` 或旧生成超过 180 秒，且轮数未满时，原子设置 `GENERATING` 并把轮数加一。第二个并发请求更新行数为 0，返回“正在生成”。消息表又有 `(conversation_id,turn_no,role)` 唯一键防止同一角色重复落库。

回答完成时，在短事务中保存助手消息、释放生成权并删除 Redis 缓存；摘要调用放到事务外的独立线程池，避免持有数据库连接等待 LLM。摘要失败时保留原消息，后续轮次可以补做。

### 需要继续改进的点

- 180 秒租约回收后，旧请求可能晚到并写入同一轮；应增加 `generation_id/fencing_token`，完成更新必须携带本次令牌。
- 当前缓存删除失败被忽略，可能短期读到旧上下文。可用 conversation `memory_version` 放入缓存 key/value，读时校验版本；或事务提交后发失效事件。
- 匿名 owner 只靠客户端自报 UUID，知道 UUID 就可能读取会话。生产应使用 HttpOnly、Secure、SameSite cookie 中的随机高熵 session，服务端绑定设备/过期策略，或要求登录。
- 健康对话应默认少存、短存、可删除，并进行字段级加密、审计和数据保留治理。

## 21. SSE 流式输出是如何工作的？与 WebSocket 有什么区别和风险？

### 主回答

客户端 POST 一条消息后，服务端返回 `text/event-stream`，依次发送 `start`、多个 `delta`、`complete` 或 `error` 事件，并在每个事件后 flush。DeepSeek 的 SSE 响应由后端逐行读取，只取 `choices[0].delta.content`，忽略 `reasoning_content`，再用有状态过滤器处理跨 chunk 的 `<think>...</think>` 标签，避免把模型内部推理展示给用户。

这个场景主要是服务端向客户端单向推送，SSE 基于 HTTP、浏览器支持和代理配置更简单；WebSocket 更适合频繁双向通信。任务状态也可以 SSE 推送，但保留 GET 轮询作为断线恢复和真相查询。

### 生产风险

- 每条 SSE 会长期占连接与线程。当前 Spring MVC `StreamingResponseBody` 加阻塞式下游 HTTP，在高并发下需要独立 executor 和容量控制；规模更大可用 WebFlux/异步 HTTP，但不能只换框架而不控制下游。
- Nginx/Ingress 要关闭缓冲、配置 idle timeout、心跳和最大连接数；当前响应已设置 `X-Accel-Buffering: no`。
- 客户端断开后写出异常，系统应尽快取消下游读取；但已经产生的 LLM 费用未必可回收。
- 一旦 token 已流给用户，就无法做完整的生成后安全审核。医疗高风险答案应先缓冲并通过规则/证据校验，再整体发送；或只流“检索中、生成中”等状态。
- 如果中途失败而已显示半段答案，不能再无缝拼接本地 fallback 造成语义混乱。应发明确 error，保存失败轮，允许用户重试。

## 22. 如何降低大模型幻觉，并保证医学场景的安全边界？

### 主回答

不能把“写了免责声明”当成安全方案。我会做分层防护：

1. 输入层：本地高召回急症规则先于所有模型，命中卒中、自伤等信号直接给固定行动指引。
2. 范围层：问题分类与越界拒答；对药物剂量、停药、确诊请求使用专门策略。
3. 证据层：只把审核知识或白名单来源提供给模型，要求答案受证据约束；检索为空宁可拒答。
4. 输出层：检查关键结论是否有来源支持、是否包含越界诊断/处方、是否遗漏急症提示；高风险结果可进入人工抽检。
5. 版本与审计：记录知识、模型、Prompt、安全规则和免责声明版本，但日志不保存完整敏感文本。
6. 评测与发布：安全测试集、红队、灰度、可回滚开关和异常率告警。

当前项目已经做到急症短路、越界拒答、检索失败安全降级、免责声明、来源展示、思考内容过滤，以及筛查引擎只返回 `INCONCLUSIVE`。尚未完整实现的是生成后医学一致性校验、严格联网白名单、人工审核闭环和生产级安全评测，因此面试中要明确这是下一阶段工作。

## 23. 联网搜索有什么安全问题？为什么“返回后过滤 URL”不够？

### 主回答

联网网页是不可信输入，可能包含过时医学信息、SEO 垃圾、提示注入、恶意跳转和私有网络 URL。若先让模型读取全网内容，再在输出里过滤 URL，恶意内容已经影响生成，过滤太晚。

生产应使用自控搜索/抓取适配器，在生成前执行：

- 域名与来源等级白名单，HTTPS、DNS 和重定向每一跳重新校验。
- 拒绝 localhost、私网、链路本地、云元数据地址，防 SSRF 和 DNS rebinding。
- 限制响应大小、类型、抓取时长和跳转次数；正文清洗与恶意指令隔离。
- 明确告诉模型网页是“数据而非指令”，与 system policy 分隔。
- 校验发布日期、机构、引用片段与最终结论；缓存时 key 包含来源和政策版本，联网答案使用短 TTL 或不缓存。

当前代码只验证提取出的来源是 HTTP/HTTPS URL，并明确提示联网资料未经审核，这还不能称为严格白名单。可靠答案应说清这个差距，而不是夸大已有能力。

## 24. 语音筛查模型具体做了什么？MFCC、TTR 能直接判断阿尔茨海默病吗？

### 主回答

当前 AI 引擎流程是：faster-whisper 中文转写；librosa 提取 13 维 MFCC 时间均值；jieba 分词后计算平均词长、TTR、平均句长和填充词频率；再把转写与特征交给 DeepSeek生成谨慎的健康筛查报告。

MFCC 描述短时频谱包络，常用于语音识别和声学分析；TTR 是不同词数/总词数，反映样本内词汇多样性，但强烈受文本长度、任务类型、ASR 错误、教育程度、方言和设备影响。它们最多是候选特征，不能单独作为患病证据。当前代码也没有训练出经过独立临床验证的分类器，LLM 生成文本更不是概率模型，所以引擎固定返回 `risk_level=INCONCLUSIVE`、`risk_score=null`。

如果要研发真正的风险模型，我会：统一看图说话任务和录音协议；按受试者划分 train/validation/test，防止同一人的录音跨集合；固定特征处理与阈值；在独立、最好外部测试集上评估；按语言、年龄、教育、性别和设备做亚组审计；对模型、数据、阈值和同意版本留痕。通过监管与临床验证前，产品仍只能称为风险筛查研究或质量检查。

## 25. 为什么不能只看准确率？你会如何验证筛查模型？

### 主回答

假设患病率只有 5%，模型全部预测阴性也有 95% 准确率，却漏掉所有阳性，所以准确率不能单独评价筛查。至少要报告：

- 灵敏度 `TP/(TP+FN)`：阳性中检出的比例，筛查通常尤其关注漏诊风险。
- 特异度 `TN/(TN+FP)`：阴性中正确排除的比例。
- PPV/NPV：与目标人群患病率密切相关，跨场景不能直接搬用。
- ROC AUC：阈值无关排序能力，但类别不平衡时还应看 PR AUC。
- Brier score 与校准曲线：分数是否能解释为风险概率；未校准就不能叫概率。
- 覆盖率：录音质检通过且模型能输出结果的比例；不能只在“容易样本”上报性能。
- 95% 置信区间、样本量依据和各亚组差异。

项目的评测脚本已经计算混淆矩阵、灵敏度、特异度、PPV、NPV、准确率、Wilson 95% CI、Brier、ROC AUC、覆盖率和分组结果；数据门禁检查 recordingId 重复、受试者跨集合、标签来源、授权和公平性字段。还需要补充 PR AUC、校准图、外部验证、漂移监测和临床效益分析。

### 数据泄漏例子

同一受试者的多段音频被随机分到训练和测试，模型可能学到说话人或设备特征，测试指标虚高。必须以 subjectId 为分组单位切分；阈值只在训练/验证集确定，不能反复观察测试集后调参。

## 26. 当前鉴权方案是怎样的？有哪些生产安全问题？

### 主回答

当前登录成功后生成 HMAC JWT，包含 username、role 和 1 小时过期时间；Redis 保存 `TOKEN:{token}->role` 和 `USER_TOKEN:{username}->token` 30 分钟并滑动续期，实现会话撤销和单设备登录。过滤器验 JWT 签名/过期，再核对 Redis 会话，把用户与角色放进 request attribute；拦截器读取 `@RequireRole` 做 RBAC。密码使用 BCrypt，新登录时会把遗留明文密码迁移为 BCrypt；登录失败 5 次锁定 10 分钟。

生产问题包括：

- 配置中存在开发数据库/RabbitMQ 密码和 JWT 回退密钥，生产必须 fail-fast 要求 Secret Manager/KMS 注入，并轮换可能暴露过的密钥。
- 自研 Filter/Interceptor 容易出现路径放行差异；应迁到 Spring Security filter chain，默认拒绝、显式放行。
- `/assistant/**` 被全局过滤器放行，再由部分 Controller 自行校验，策略分散；匿名会话 UUID 不是可靠凭证。
- 找回密码仅核对姓名和手机号，容易被社会工程攻击；应使用经过验证的 OTP/邮件、风控、限速和通知，管理员启用 MFA。
- 登录失败 key 只按 username，攻击者可恶意锁定他人；应结合 IP、设备、账号分层限流，并防用户枚举。
- 修改密码或重置密码后应撤销现有 token；Token 密钥要支持 `kid` 与轮换。

RBAC 只表达角色，医疗数据还需要对象级授权：每次按 `resource.user_id=currentUserId` 查询。项目筛查、音频和 PDF 多处已经做归属校验，未授权资源通常返回 404，减少资源枚举。

## 27. 音频上传会有哪些攻击面？当前代码如何防护，还缺什么？

### 主回答

攻击面包括路径穿越、伪造扩展名/Content-Type、超大文件、压缩炸弹或解析器漏洞、恶意 WAV 头、资源耗尽、覆盖已有文件和越权读取。

当前防护：

- Spring multipart 限 25 MB，请求 26 MB；Validator 再校验实际大小。
- 检查 RIFF/WAVE 魔数，并用 Java Sound 解析 PCM 格式、帧数和时长；限制 1～300 秒、8～48 kHz、1～2 声道及合法位深。
- 文件名由服务端 userId + timestamp + UUID 生成，不使用原始文件名。
- `StoragePaths` 拒绝绝对路径、多级路径和越出根目录的 normalize 结果。
- 文件写成功但数据库保存失败时删除落盘文件；读取前校验数据库归属。

仍需补充：网关层请求体和速率限制；上传流式处理，避免内存缓存；恶意文件扫描/沙箱解码；磁盘配额与水位；对象存储隔离；checksum 和重复内容策略；上传中的临时文件与孤儿清理；所有解析库的依赖扫描。音频质检目前要求至少 20 秒，而上传只要求至少 1 秒，这种策略差异应在前端明确或在上传阶段统一，否则用户会上传成功后才得到“质量不足”。

## 28. 如何处理语音、转写和报告这些敏感数据？删除接口能做到彻底删除吗？

### 主回答

语音、转写、筛查结果和健康对话都属于敏感健康相关信息。数据治理要从目的限定开始：上传前记录明确同意、版本、时间和任务类型；只采集筛查所需数据；全链路 TLS；数据库、对象存储、备份用 KMS 加密；按用户归属和内部服务身份授权；日志不写 Token、完整转写和报告；设置保留期限、审计、导出与删除流程；还要评估第三方模型的数据使用和区域合规。

当前上传已经强制同意版本，读取/删除校验用户归属，删除音频时联动删除本地音频、报告和 PDF，并阻止活动任务期间直接删除。但本地文件删除和数据库事务不是原子的，而且还要覆盖 artifact、Redis 缓存、对象存储版本、备份、日志和第三方副本，所以不能简单承诺“HTTP 返回后所有字节瞬间消失”。

生产删除应是可追踪工作流：

```text
用户请求 -> 鉴权与冻结资源 -> 写 deletion_request + Outbox
-> 各存储消费者幂等删除/加密擦除
-> 清缓存、撤销签名 URL、停止未完成任务
-> 汇总状态与审计证明 -> 在约定 SLA 内完成
```

备份通常按生命周期自然到期并禁止业务恢复后重新出现已删数据；若法规与架构允许，可对单用户数据使用独立数据密钥，通过销毁密钥实现 crypto-shredding。审计日志只记录删除动作和脱敏标识，不继续复制被删正文。

## 29. 你会如何建设高可用、可观测和故障恢复？

### 主回答

我会先定义 SLI/SLO，再决定冗余和告警，而不是只说“部署集群”。示例 SLI 包括 API 可用率、任务受理 P95、任务完成成功率/时长、最老队列消息年龄、报告可下载率和 RAG 安全回答率。

部署上：API 至少两个跨故障域无状态副本；MySQL 多可用区、binlog、全量+增量备份和 PITR；Redis 高可用；RabbitMQ 三节点 Quorum Queue；对象存储多副本；Qdrant replication factor 至少 2；Worker 跨节点反亲和。API 用 readiness/liveness/startup probe，Worker 按队列指标扩容，发布使用滚动或金丝雀。

可观测上用 OpenTelemetry 传播 traceId/taskId，贯穿 HTTP、数据库、Outbox、RabbitMQ、Python、Embedding、Qdrant、DeepSeek 和 PDF。重点指标：

- RED：请求 rate、errors、duration；USE：CPU/内存/磁盘/连接池使用率与饱和度。
- RabbitMQ ready/unacked、最老消息年龄、publish confirm 延迟、重试和 DLQ。
- 每个筛查阶段排队/执行时长、Worker 心跳、GPU 利用率/OOM。
- Outbox 未发布年龄；线程池 active/queue/rejected；MySQL 慢查询和连接池等待。
- RAG Recall@K、阈值拒绝、降级率、引用支持率、LLM 429/超时/token/费用。

恢复必须演练：定期从备份恢复到隔离环境并验证 RPO/RTO；重启 Worker 验证未 ACK 消息重投；模拟 RabbitMQ、DeepSeek、Qdrant、Redis 故障确认降级；扫描卡在非终态且超过 SLA 的任务，根据阶段 artifact 决定继续、重试或失败。只有备份没有恢复演练不算灾备。

## 30. 线上用户反馈“任务一直卡在 70%”，你如何排查和止损？

### 主回答

我先把 70% 映射到代码状态：`LLM_ANALYZING`。然后用 taskId 查任务的 status、attempt、updatedAt、traceId；查同 traceId 的 Outbox、RabbitMQ、Python Worker 和下游 DeepSeek，而不是直接重启所有服务。

排查顺序：

1. 看影响范围：单任务、单 Worker、单模型还是全量；检查错误率、队列年龄、DLQ 和最近发布。
2. 看任务前一阶段 artifact 是否存在、SHA-256 是否正确，确认是否真的完成 ASR/特征。
3. 看 RabbitMQ：请求队列 ready/unacked、consumer 数、连接、内存/磁盘 alarm、retry queue 和 DLQ；unacked 长期不降可能是 Worker 卡死。
4. 看 Worker：进程心跳、线程/进程栈、GPU 显存和利用率、OOM、外部 API 超时；检查 attempt 与 messageId，日志只用脱敏 ID。
5. 看 DeepSeek：DNS/TLS、429、5xx、连接池、read timeout、账户额度和熔断状态。
6. 看状态投影：完成事件是否已发布但 Java status listener 消费失败；检查 `consumed_event` 与事务回滚，避免“已去重但业务未落库”的假象。

### 止损和恢复

- 下游普遍故障时暂停/降低 LLM consumer 并发，打开熔断，避免重试风暴和费用扩大；API 继续受理还是返回 503 取决于队列年龄与容量预算。
- 对超过 SLA 的任务显示“延迟”而不是永远 70%；允许用户取消。
- 若请求可安全重试，使用延迟队列和抖动；永久配置错误直接失败并告警，不反复重试。
- 对已有有效 artifact 的任务幂等重放完成事件；没有 artifact 的任务按 attempt 重试。禁止直接手工改 `COMPLETED`。
- 事故后补充 watchdog：扫描 `updated_at` 超时的非终态任务；增加 LLM 阶段 deadline、Worker heartbeat、最老 unacked 告警和故障注入回归。

面试时最后补一句：排障的目标不只是“恢复服务”，还要保护用户数据、避免重复扣费、给出可解释状态，并通过时间线和根因分析形成长期修复。

- Kubernetes、多副本 API、三节点 RabbitMQ、MySQL/Redis/Qdrant 高可用。
- 对象存储、预签名 URL、跨存储删除工作流。
- Spring Security/OIDC、MFA、生产 Secret Manager 和密钥轮换。
- Redis 分布式限流、Resilience4j 熔断/Bulkhead、完整预算系统。

- 经临床验证、可输出风险等级或概率的模型。

### 最容易失分的说法

- “用了 MQ，所以消息绝不重复。”正确说法是至少一次投递与幂等。
- “加了 `@Transactional`，数据库和文件就一致。”文件/对象存储不参与 MySQL 事务。

- “准确率高就能上线。”筛查必须同时讨论灵敏度、特异度、覆盖率、校准、CI 和外部验证。

- “微服务越多越先进。”应按资源、团队、发布和故障边界拆分。
- “上 Kubernetes 就高可用。”还需要外置状态、多故障域、探针、PDB、备份恢复和 SLO。

第一轮先熟练 1、2、3、5、6、17、24、30，保证项目介绍和核心链路能讲清。第二轮练 7～16 的并发与一致性追问。第三轮练 18～29 的 RAG、模型、安全和生产化。每道题先在 90 秒内给结论、证据、权衡，再根据面试官追问展开，不要一开始把所有细节全部倒出。
