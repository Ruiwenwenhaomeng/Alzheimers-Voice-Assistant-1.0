# 生产级分布式系统改造方案

## 1. 总体判断

当前项目不需要立即拆成十几个业务微服务。更合适的目标是先建设：

```text
无状态模块化后端 + 独立 AI Worker + 外置状态 + 高可用基础设施
```

当前业务规模下，过早拆分用户服务、报告服务和 RAG 服务，会显著增加分布式事务、接口治理和运维复杂度。先让 Spring Boot API 能够无状态横向扩容，再根据团队边界、独立发布需求和真实负载决定是否继续拆分。

## 2. 当前基础与主要阻塞

项目已经具备较好的异步基础：

- `screening_task` 任务状态；
- Outbox 可靠事件投递；
- RabbitMQ 消息队列；
- 幂等键和消费者去重；
- 自动重试和死信队列；
- 后台 Python 筛查；
- Java 后台生成 PDF；
- 前端任务轮询。

真正阻碍生产上线的主要问题是：

| 当前状态 | 生产目标 |
| --- | --- |
| 音频、PDF、分析产物写本机目录 | S3/MinIO 对象存储 |
| MySQL、Redis、RabbitMQ、Qdrant 都是单节点 | 托管高可用或多节点集群 |
| 数据库迁移依赖手工执行 | Flyway 自动迁移 |
| 自研 JWT 和拦截器 | Spring Security + OIDC |
| Python 单个 Worker 串行完成全部 AI 阶段 | 按资源类型拆分 Worker 池 |
| 应用首次请求懒建 Qdrant 索引 | 离线构建、版本化发布、别名切换 |
| 没有正式 Dockerfile 和 CI/CD | 标准镜像、自动测试、扫描和部署 |
| 缺少完整链路追踪和生产告警 | OpenTelemetry、指标、日志和 Trace |
| 配置存在开发密码和 JWT 回退密钥 | Secret Manager/KMS，生产禁止默认值 |

数据库默认配置目前位于 `backend/src/main/resources/application.yml`，JWT 回退密钥位于 `backend/src/main/java/com/alz/config/JwtUtil.java`。生产改造开始前应轮换可能已经使用过的数据库、JWT、RabbitMQ 和第三方 API 密钥，并禁止生产配置回退到开发默认值。

## 3. 目标架构

```text
用户
  │
CDN / WAF / HTTPS Ingress
  │
Spring Boot API × 2+
  ├─ 用户、权限、任务、报告、RAG 编排
  ├─ MySQL：业务最终真相
  ├─ Redis：缓存、限流、短期状态
  ├─ 对象存储：音频、PDF、分析产物
  └─ Outbox
       │
RabbitMQ 三节点 Quorum Queue
  ├─ 音频质检 Worker
  ├─ Whisper 转录 Worker
  ├─ 特征分析 Worker
  ├─ LLM 筛查 Worker
  └─ PDF 报告 Worker

RAG 链路
  ├─ Embedding Worker
  ├─ Qdrant 集群
  ├─ 知识发布/索引 Worker
  └─ DeepSeek/联网检索适配器

所有组件
  └─ OpenTelemetry → 指标、日志、Trace、告警
```

核心原则是任何 API 实例都不保存本地业务状态。业务状态只存放在 MySQL、对象存储等受控持久化系统中；RabbitMQ 只负责可靠传输和削峰，Redis 只保存可重建的缓存与协调数据，Qdrant 是可以从审核知识重建的派生索引。

## 4. 应用边界与部署单元

### 4.1 Spring Boot API

Spring Boot API 初期继续采用模块化单体，但至少运行两个无状态副本。它负责：

- 用户和权限；
- 音频元数据；
- 筛查任务受理与查询；
- 报告权限控制；
- RAG 同步编排；
- 事务 Outbox；
- 对象存储签名 URL；
- 医疗安全规则和急症拦截。

API 进程不应直接承担 PDF 生成、长时间转录或模型推理。可以先在同一代码仓库中使用不同 Spring Profile，把 API 和 Java 消费 Worker 部署为不同进程，而不必立即拆成多个仓库。

### 4.2 Python Worker

Python Worker 使用独立 Deployment，不监听公网端口，仅通过 RabbitMQ 接收任务，并从受控对象存储读取输入、写入产物。

根据负载逐步拆成：

- 音频质检 Worker；
- Whisper 转录 Worker；
- 语音特征 Worker；
- LLM 分析 Worker。

这样可以分别控制 CPU、内存、GPU 和第三方 API 并发。

### 4.3 Embedding 和知识索引

Embedding 服务独立部署，可根据资源情况调度到 CPU 或 GPU 节点。知识索引由后台 Job 或索引 Worker 构建，不能由用户的第一次查询触发。

知识发布流程应支持：

```text
审核通过
→ 构建新版本索引
→ 离线评测
→ Qdrant alias 切换
→ 监控
→ 必要时回滚旧版本
```

## 5. 存储和基础设施

### 5.1 对象存储

当前音频、PDF 和筛查产物依赖本机目录，这会导致任务在不同节点间调度时找不到文件。应增加统一的 `ObjectStorageService` 抽象，并迁移到 S3、MinIO 或云对象存储。

对象存储需要支持：

- 服务端加密；
- 生命周期和自动过期；
- 版本控制；
- 预签名上传和下载；
- 文件大小、格式和 SHA-256 校验；
- 用户权限校验；
- 删除事件传播；
- 审计日志。

音频二进制和完整报告不应进入 RabbitMQ、Redis或普通应用日志。

### 5.2 MySQL

MySQL 是用户、任务、报告、Outbox 和审计数据的最终真相源。

优先选择云厂商多可用区托管 MySQL；自建时应使用经过验证的高可用方案。至少需要：

- 主从或 InnoDB Cluster；
- 自动故障转移；
- binlog；
- 全量和增量备份；
- 时间点恢复；
- 备份加密；
- 定期恢复演练；
- 数据库连接池和慢查询监控。

参考资料：

- [MySQL 8.4 Backup and Recovery](https://dev.mysql.com/doc/refman/8.4/en/backup-and-recovery.html)
- [MySQL Point-in-Time Recovery](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery.html)

### 5.3 RabbitMQ

生产环境推荐三个 RabbitMQ 节点和 Quorum Queue，并使用快速持久化磁盘。

可靠性要求：

- publisher confirm；
- mandatory publish 和 returned message 处理；
- 消费者手动 ACK；
- 消费成功落库或落对象存储后再 ACK；
- 有界 prefetch；
- 延迟重试队列；
- 专属 DLQ；
- 消息年龄和队列深度告警；
- 独立 vhost、最小权限账号和 TLS。

RabbitMQ 提供的是至少一次处理链路，不能假设消息只处理一次。publisher confirm 和 consumer acknowledgement 分别覆盖不同方向的可靠性。

参考资料：

- [RabbitMQ Quorum Queues](https://www.rabbitmq.com/docs/quorum-queues)
- [RabbitMQ Consumer Acknowledgements and Publisher Confirms](https://www.rabbitmq.com/docs/next/confirms)

### 5.4 Redis

Redis 只保存可重建数据，例如：

- 登录风险计数；
- 分布式令牌桶；
- 热点任务状态；
- 短期会话摘要；
- 答案缓存；
- 预算计数；
- 短期分布式协调。

任务最终状态和报告不能只存在 Redis。生产可以采用托管 Redis，或主从复制加至少三个 Sentinel。

参考资料：[Redis Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

### 5.5 Qdrant

Qdrant 中只保存可由审核知识重建的索引。正式高可用部署建议：

- 多节点分布式模式；
- 合理的 shard 数量；
- replication factor 至少为 2；
- 节点反亲和；
- 负载均衡；
- API Key、TLS 和网络隔离；
- 定期快照；
- collection 版本和 alias；
- 索引构建完成后的 readiness 校验。

启用 Qdrant 分布式模式不会自动为已有数据创建副本，需要明确配置复制和数据迁移。

参考资料：[Qdrant Distributed Deployment](https://qdrant.tech/documentation/scaling/distributed_deployment/)

## 6. 筛查事件链路

当前组合 Worker 可以作为迁移中间态。达到一定负载后，建议拆成版本化事件：

```text
screening.requested.v1
  → audio.validated.v1
  → transcription.completed.v1
  → features.completed.v1
  → analysis.completed.v1
  → report.generated.v1
```

每个阶段都应：

- 使用明确的 Schema 和版本；
- 只传递 ID、受控对象引用和必要摘要；
- 持久化输入、输出版本和 SHA-256；
- 使用 `eventId + consumerName` 幂等；
- 区分可重试错误和永久错误；
- 采用指数退避和抖动；
- 超过次数后进入专属 DLQ；
- 支持取消检查点；
- 记录 Worker 心跳；
- 允许超时任务自动回收或继续执行。

多个 Outbox Publisher 实例需要使用数据库租约、行锁或 `SKIP LOCKED`，避免重复并发发布；即使发生重复发布，消费者仍必须保持幂等。

## 7. Kubernetes 部署

建议使用 Kubernetes 或等价的托管容器平台运行自有服务：

- Spring API：Deployment，至少两个副本；
- Python Worker：按任务类型独立 Deployment；
- Embedding：独立 Deployment，按节点标签调度；
- 索引构建：Job；
- 清理和备份检查：CronJob；
- 配置：ConfigMap；
- 密钥：Secret Manager CSI 或等价机制；
- 网络：Ingress/Gateway、NetworkPolicy；
- 中断控制：PodDisruptionBudget；
- 节点故障隔离：pod anti-affinity 和 topology spread。

每个服务都需要 startup、readiness 和 liveness 探针。API 可按 CPU、内存或请求速率使用 HPA；Worker 更适合按 RabbitMQ 队列深度和任务等待时间扩缩容。

参考资料：

- [Kubernetes Workloads](https://kubernetes.io/docs/concepts/workloads/)
- [Kubernetes Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)
- [Kubernetes Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/)

团队规模较小时，建议优先购买托管 MySQL、Redis、RabbitMQ 和对象存储，只在 Kubernetes 中运行 API、Worker、Embedding 和索引任务。

## 8. 认证与安全

### 8.1 身份认证

建议使用 Spring Security，并接入 OIDC/OAuth 2.0 身份提供方。可选择 Keycloak 或云厂商身份服务。

需要提供：

- 短期访问令牌；
- Refresh Token 轮换；
- 管理员 MFA；
- 登录风控和分布式限流；
- 可靠的短信、邮件或人工核验找回流程；
- 用户、管理员和内部服务不同权限；
- Token 密钥轮换；
- 服务账户和工作负载身份。

当前仅凭姓名与手机号匹配即可重置密码的方式不适合生产环境。

### 8.2 数据安全

医疗健康信息属于敏感个人信息。生产环境至少需要：

- 用户告知和明确授权；
- 目的限定和数据最小化；
- 全链路 TLS；
- 内部 mTLS 或工作负载身份；
- 数据库、对象存储和备份使用 KMS 加密；
- 密钥和业务数据分离；
- RBAC/ABAC；
- 不可篡改审计日志；
- 保存期限和自动清理策略；
- 用户查询、导出和删除能力；
- 第三方模型数据流向与跨境/区域合规评估；
- 定期权限审计和渗透测试。

参考资料：[中华人民共和国个人信息保护法](https://www.jsmm.gov.cn/u/cms/www/202110/1317253417oi.pdf)

### 8.3 医疗安全边界

- 系统定位为风险筛查和健康教育，而不是确诊工具；
- 急症识别和安全拒答采用本地确定性规则；
- 即使 LLM、Qdrant 或联网搜索不可用，也必须返回安全结果；
- 记录模型、提示词、特征、知识和规则版本；
- 对结果进行引用校验和医学安全检查；
- 新模型和新知识版本经过离线评测、灰度和人工审核；
- 如果对外宣称诊断或治疗决策支持，应单独评估医疗器械监管和临床验证要求。

## 9. 可观测性

使用 OpenTelemetry 统一 Java、Python、HTTP、RabbitMQ、Qdrant、Embedding 和 LLM 的 Trace Context。

建议建设：

- OpenTelemetry Collector；
- Prometheus；
- Grafana；
- Loki、ELK 或等价日志平台；
- 错误聚合和告警平台。

需要重点观测：

- API QPS、错误率和延迟；
- JVM、线程池和数据库连接池；
- RabbitMQ ready、unacked、消息年龄、重试和 DLQ；
- 各筛查阶段排队及执行时间；
- Worker 心跳和任务超时；
- Embedding 延迟、批大小和显存；
- Qdrant 查询延迟、命中率和阈值拒绝率；
- DeepSeek 调用量、429、超时、费用和熔断状态；
- RAG 召回、引用覆盖和安全拦截率。

日志不得记录完整 Token、音频、转录和健康报告。应使用 `traceId`、`taskId` 和脱敏 `userId` 关联链路。

参考资料：[OpenTelemetry Java](https://opentelemetry.io/docs/languages/java/)

## 10. CI/CD 和数据库迁移

每个服务应提供独立 Dockerfile，并采用固定版本、非 root 用户和多阶段构建。

流水线至少包括：

1. Java、Python 和前端单元测试；
2. Testcontainers 集成测试；
3. API 和消息契约测试；
4. 依赖漏洞扫描；
5. Secret 扫描；
6. SBOM 生成；
7. 镜像漏洞扫描和签名；
8. 部署到测试环境；
9. 数据库迁移和冒烟测试；
10. 灰度或滚动发布；
11. 自动或人工批准生产发布；
12. 失败自动回滚。

数据库变更迁移到 Flyway 管理。迁移脚本应满足向前兼容，推荐遵循“先扩展、后迁移数据、最后收缩”的流程，避免新旧应用同时运行时发生 Schema 不兼容。

## 11. 灾备和上线验收

上线前先根据业务确定 SLO、RPO 和 RTO。例如：

- 核心 API 可用性目标；
- 任务受理延迟；
- 筛查任务最长排队时间；
- 数据最多允许丢失多久；
- 单节点、单可用区或区域故障后的恢复时间。

必须完成以下演练：

- 随机停止一个 API Pod；
- 停止一个 RabbitMQ 节点；
- Redis 故障并验证回退 MySQL；
- Qdrant 不可用并验证安全降级；
- Worker 处理完成但 ACK 前退出；
- DeepSeek 超时、429和不可用；
- MySQL 时间点恢复；
- 对象存储恢复；
- 删除用户数据并验证所有副本、缓存和派生产物；
- 长时间压力和队列积压测试；
- 权限越权、Prompt Injection、恶意文件和 SSRF 测试。

备份只有经过恢复演练才有意义。恢复流程应形成运行手册，并明确值班人员、操作步骤和回滚条件。

## 12. 分阶段实施

### 阶段一：生产安全基线

- 轮换并移除默认密钥；
- Spring Security/OIDC；
- Flyway；
- 对象存储抽象；
- 生产配置启动校验；
- 用户数据保存和删除策略。

### 阶段二：容器化和交付

- Java、Python Worker、Embedding 和前端 Dockerfile；
- CI/CD；
- 镜像扫描、SBOM 和签名；
- 独立测试环境；
- 自动迁移、冒烟和回滚。

### 阶段三：单区域高可用

- 至少两个 API 实例；
- 托管或高可用 MySQL；
- 高可用 Redis；
- 三节点 RabbitMQ Quorum Queue；
- 对象存储；
- Qdrant 备份或分布式集群；
- Kubernetes 探针和自动扩缩容。

### 阶段四：异步链路生产化

- Worker 心跳和任务回收；
- 队列深度限流；
- 超时、熔断和 Bulkhead；
- 分类重试和独立 DLQ；
- 根据资源瓶颈拆分 Worker；
- 端到端幂等和故障演练。

### 阶段五：RAG 知识治理

- PDF/论文入库；
- 人工审核后台；
- 混合检索和重排；
- 索引版本和别名切换；
- 引用、召回和安全评测；
- 受控联网检索。

### 阶段六：可观测性、灾备和灰度上线

- OpenTelemetry；
- 指标、日志、Trace 和告警；
- 压力测试和容量规划；
- 备份恢复演练；
- 安全测试和医学内容审核；
- 小流量灰度、监控和逐步放量。

## 13. 最优先的代码工作

建议优先落地以下六项：

1. 对象存储抽象；
2. Flyway 自动迁移；
3. Spring Security/OIDC；
4. 生产 Dockerfile 和 CI/CD；
5. API 与 Worker 部署角色拆分；
6. OpenTelemetry 链路追踪。

完成这六项后，系统才能真正具备多节点部署、横向扩容、可观测和可恢复的基础，再继续拆分 Worker、建设高可用集群和完善 RAG 治理。
